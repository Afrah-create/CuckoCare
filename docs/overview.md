# CucoCare — how the app works

CucoCare is an **offline-first Android app** for smallholder poultry farmers in Uganda, plus a **vet portal in the same app**. Farmers keep batches, vaccination, feed, losses, and health incidents on the phone even with no signal. When data returns, changes sync to **Supabase**. Veterinary officers see nearby requests, accept cases, and message the farmer on that case.

This document is the general map of the product, tech stack, architecture, and features. Deeper contracts live in [architecture.md](architecture.md), [case-messaging.md](case-messaging.md), [vet-directory.md](vet-directory.md), and the [ADRs](adr/).

---

## Who uses it

| Role | After sign-in | What they do |
|------|----------------|--------------|
| **Farmer** | Today tab (`/today`) | Run the farm: flocks, vaccines, feed, records, find a vet, request help, chat on an accepted case |
| **Veterinary professional** | Requests tab (`/vet`) | See farmer requests, map, active visits, profile, chat with the farmer on accepted cases |

Role is stored on `profiles.app_role` (`farmer` or `vet`). The same Flutter binary switches shells. Vets are **not** farm members.

## Tech stack

| Layer | Choice | Why |
|-------|--------|-----|
| Client | Flutter (Dart 3), Android first (minSdk 24) | One codebase, works offline |
| UI state | Riverpod | Providers sit between widgets and data |
| Navigation | go_router (typed routes) | Role-based shells, deep links from notifications |
| Local database | Drift (SQLite) | Source of truth on the device |
| Backend | Supabase (Postgres, Auth, Storage, Edge Functions, Realtime) | Sync target, RPCs, photos, optional push |
| Identity | Email OTP / password via Supabase Auth | Session on device; demo session in **dev** only |
| Maps | flutter_map + OpenStreetMap tiles | Vet request map |
| Location | geolocator | Farm GPS and vet GPS (optional) |
| Photos | image_picker + `image` | Incident photos and case chat; EXIF/GPS stripped for chat |
| Reminders | flutter_local_notifications + Workmanager | Vaccination due, even if the process was killed |
| Optional push | Firebase Cloud Messaging (HTTP v1) | Generic “new message on your vet request” |
| Optional SMS | `sms_outbox` + `sms-dispatch` (MakyReach stub) | Urgent case fallback when the vet is silent |

**Flavors:** `dev`, `staging`, `prod`. Secrets for Flutter come from `env/{flavor}.json` generated by `dart run tool/sync_env.dart` (service role stays out of the client).

## Architecture

```
Widgets  →  Riverpod providers  →  Repositories / domain  →  Drift (local)
                                                              │
                                                         SyncEngine
                                                              │
                                                    Supabase (Postgres RPCs)
```

**Rules that keep the app maintainable:**

- Widgets do not import Drift, Supabase, or HTTP.
- Repositories read and write **Drift**. Synced writes also enqueue an **outbox** row in the same transaction (`writeSynced`).
- Domain code is pure Dart (no Flutter / Drift / Supabase).
- IDs are **client UUID v7**. The server never mints row IDs.
- Dates are stored; ages are computed at read time.
- Farm data is isolated: `sync_push` authorises against **membership** and the **stored** `farm_id`, not a spoofed payload field.

Per-farm `server_version` counters drive **pull**. The client remembers the last version it applied per farm scope and asks for newer rows. Push is an ordered list of ops (`upsert` / `delete`) with idempotent `op_id`s.

Special cases:

- **Farmers** write `case_messages` through a `sync_push` hook that derives `farm_id` from the request and forces `sender_role = farmer`.
- **Vets** are not members, so they send with `SECURITY DEFINER` RPCs (`send_case_message`, and so on) and hydrate with `pull_assigned_case_messages`.
- **Feed stock is never stored.** It is derived from transactions in `FeedMetrics.compute`.

Conflict handling is last-writer-wins on `server_version` for mutable tables. Append-only tables insert once. Soft deletes (`deleted_at`) travel so other devices tombstone the same row.

Realtime (where enabled) is only a **hint** to pull. The phone does not treat a socket as the database.

## How a change leaves the phone

1. User saves (batch, incident, message, …).
2. Drift row + outbox row in one transaction.
3. UI shows the local data immediately (queued clock on unsent chat).
4. `SyncScheduler` runs when online (after writes, on foreground, on connectivity).
5. `sync_push` applies ops (parents before children: farm → batch → health → request → messages).
6. Ack sets `server_version` on the local row; outbox row is deleted.
7. The other party’s device pulls (or gets a Realtime/FCM hint) and merges.

If the op is rejected as non-retryable, it is stored in `sync_ops_applied`. Retry must use a **new** `op_id`.

## Authentication and accounts

- Sign in / sign up with email. OTP and password paths both exist.
- Forgot password uses the same auth stack.
- Each signed-in user gets a **per-account Drift file** (`AppDatabase.forAccount`).
- Profiles carry display name, phone, and `app_role`.
- **Dev** can use **Continue with offline demo session** (no real Supabase user; sync is skipped).
- Farm members have roles: owner, manager, worker, viewer. Viewers can read some threads but cannot send Case Radio messages.

## Farmer app

Bottom tabs: **Today · Batches · Feed · Records · More**.

### Today

Home for the day: greeting, farm banner, getting-started if the farm is empty, counts (birds, due vaccines, open incidents), unread case messages, and shortcuts into batches or records.

### Batches (flocks)

A batch is one flock: name, bird type, head count, acquired date, age at acquisition, hatchery vaccines, programme.

- Create / edit / close a batch.
- **Vaccination calendar** is generated from a programme (steps + due dates). Tasks can be marked done, skipped, or assumed done with monotonic status rules.
- **Losses / mortality** (editable after the fact) feed remaining bird counts.
- **Report a health incident** from the batch (symptoms, photos, optional vet request).

Age is computed from `acquired_on` + `age_at_acquisition_days`, not stored as a number that goes stale.

### Feed

Catalogue of feed items (name, type, unit, reorder level) and **transactions**: purchase, consumption, wastage, signed adjustment.

The list shows derived quantity and cost. Negative raw quantity is flagged as inconsistent rather than silently stored as stock. Optional shareable feed report.

### Records

Two sections:

- **Health** — incidents (summary, symptoms, photos, linked vet request status, pending-sync badge). Draft vet requests can be published later.
- **Mortality** — loss history across batches.

Unread case-message badges appear on incident rows when a thread exists.

### Farm profile (More)

Name, district, village, phones, GPS. Location is used for Find a Vet distances, map pins (if the farmer shares location on a request), and visit routing.

### Find a Vet

Lists **verified, active, opted-in** officers. Farmers see name, organisation, district, services, phone, and `distance_km` — **never** raw vet coordinates. Call / SMS / WhatsApp stay here. Directory results cache ~7 days for offline.

### Health incidents and vet requests

Reporting an incident writes a `health_records` row (`record_kind = incident`) and a `vet_assistance_requests` row.

| Farmer choice | Request status |
|---------------|----------------|
| Request a vet | `submitted` (inbox) |
| Save only | `draft` (device until published) |

Optional: directed to a specific vet, service type (consultation / farm visit / either), share farm GPS, urgency when many birds are affected.

**Request lifecycle (server-controlled for vet statuses):**

`draft` → `submitted` / `received` → `accepted` → `in_progress` → `completed`  
or `declined` / `cancelled`

Farmers cannot push `accepted` themselves. After the vet accepts, **Case Radio** opens.

### More (other)

Appearance (theme), notification settings, subscription placeholder, sign out.

## Vet portal

Bottom tabs: **Requests · Map · Active · More**.

### Requests

Inbox of open assistance requests the vet is allowed to see:

- **Broadcast** (no requested vet, unassigned)
- **Directed to this vet**
- Hidden once assigned to someone else

Filters: All, New (`submitted`), For you, Urgent, plus **service type** and **symptom** chips. Stats: new, active, in progress, directed, urgent.

Actions: open incident (photos, notes, symptoms), Accept, Decline. Accept assigns the vet, inserts a system chat line, and opens the farmer thread.

### Map

Same visibility rules, including completed visits. Pins only when the farmer shared location **and** the farm has coordinates.

### Active

Cases this vet accepted that are `accepted` or `in_progress`. Message the farmer, start the visit, mark complete. Same incident filters as Requests.

### More / profile

Name, organisation, district, phone, consultation vs farm visit, availability, opt-in. GPS so farmers can sort by distance. Unverified vets stay off Find a Vet until `admin_set_vet_verified`.

## Case Radio (farmer ↔ assigned vet chat)

One thread **per assistance request**, not a social inbox.

| Request status | Chat |
|----------------|------|
| Waiting (`submitted` / `received`) | Read-only — “waiting for acceptance” |
| `accepted` / `in_progress` | Farm sending roles + assigned vet |
| Closed | Archive, read-only |

- Text, photos, and **system** lines (e.g. “X accepted your request”).
- No edit, delete, reactions, typing indicators, or E2E encryption.
- Delivery: queued → sending → sent → seen (derived from outbox + read cursors).
- Photos adapt to link quality (smaller / deferred on poor or metered + data saver).
- Unread counts are **derived** in `MessageMetrics` (badges on Today, Records, Requests, nav).
- Push payloads are generic (“New message on your vet request”) with `{type, request_id}` only.
- Urgent cases can enqueue **one SMS per rule per 24 hours** (accept SLA / reply SLA) via `sms_outbox`. Dispatch is stubbed until MakyReach is configured.

Details: [case-messaging.md](case-messaging.md).

## Notifications and reminders

- **Local:** vaccination due / overdue, scheduled in the Android timezone (Kampala-aware calendar where documented).
- **Case messages:** FCM when Firebase is wired (`docs/push-setup.md`). If Firebase is absent, `kPushAvailable = false` — in-app sync and polling still work.
- Settings: per-channel prefs including vet messages.
- Notification tap builds the existing back stack (Today/Records → incident/request → messages).

## Layout and UI conventions

- `AppPage`, spacing tokens, and theme from `ColorScheme` — screens should not hard-code colors.
- Phone, landscape, and tablet (rail) layouts share the same destinations.
- Pull-to-refresh, skeletons, empty states, and snackbars follow shared widgets.
- Sync badge in the app bar (idle / syncing / offline / error).

## What is intentionally not in the product (yet)

- iOS production IPA
- Outbreak geocast / district-wide alerts
- End-to-end encryption of chat
- Chat on Find a Vet (contact is phone / WhatsApp)
- Farmer–farmer social feed
- Live subscription billing
- Production MakyReach SMS until sender ID and webhooks are set

## Running it

```bash
cp .env.example .env          # Supabase URL + anon key
dart run tool/sync_env.dart prod
flutter pub get
dart run build_runner build
flutter run --flavor prod --dart-define-from-file=env/prod.json
```

Dev shortcut: `./scripts/run_dev.sh`. Quality: `flutter analyze` and `flutter test`.

New backend behaviour needs a **new numbered migration** applied to the hosted project (SQL editor or Supabase CLI). The Flutter client alone cannot change `sync_push` or `vet_inbox`.
